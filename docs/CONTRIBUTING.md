# CONTRIBUTING.md

# Contributing Guide

## MiMo Web Toolkit

Версия: 1.0

---

# Назначение

Данный документ определяет правила участия в разработке проекта **MiMo Web Toolkit**.

Он обязателен как для людей-разработчиков, так и для AI-агентов (MiMo Code, ChatGPT, Claude Code, Gemini CLI и других), участвующих в развитии проекта.

Главная цель — сохранить архитектурную целостность, единый стиль и высокое качество кода.

---

# Основной принцип

Перед изменением проекта необходимо:

1. изучить `PROJECT_SPEC.md`;
2. изучить `ARCHITECTURE.md`;
3. изучить `ROADMAP.md`;
4. изучить `CODING_STANDARDS.md`.

Если предлагаемое изменение противоречит этим документам, необходимо:

* объяснить причину;
* предложить альтернативу;
* получить подтверждение перед внесением изменений.

---

# Порядок работы

Каждая задача должна выполняться в следующем порядке:

1. Проанализировать запрос.
2. Проверить влияние на архитектуру.
3. Определить затрагиваемые модули.
4. Предложить решение.
5. Реализовать изменение.
6. Проверить совместимость.
7. Обновить документацию (если требуется).

---

# Работа по этапам

Проект развивается поэтапно.

Каждый этап должен завершаться полностью рабочим состоянием.

Не допускается начинать следующий этап, пока предыдущий не завершён.

---

# Изменение архитектуры

Если существует более удачное архитектурное решение:

1. объяснить преимущества;
2. описать последствия;
3. показать влияние на существующие компоненты;
4. предложить план миграции;
5. дождаться подтверждения;
6. только затем изменить архитектуру.

---

# Работа с существующим кодом

Перед изменением существующего файла необходимо:

* понять его назначение;
* проверить зависимости;
* сохранить обратную совместимость, если это возможно.

Изменения должны быть минимально необходимыми.

---

# Создание новых модулей

Каждый новый модуль должен:

* иметь одну зону ответственности;
* содержать docstring;
* использовать type hints;
* соответствовать `CODING_STANDARDS.md`;
* сопровождаться обновлением документации, если меняется публичное поведение.

---

# Работа с MCP

Каждый новый MCP-инструмент должен:

* быть независимым модулем;
* иметь чёткое описание;
* использовать единый формат входных и выходных данных;
* корректно обрабатывать ошибки;
* логировать свою работу.

---

# Работа с ComfyUI

Все обращения к ComfyUI должны выполняться только через единый клиент (`comfy_client.py`).

Запрещается выполнять HTTP-запросы к ComfyUI из других модулей.

---

# Работа с конфигурацией

Любые новые настройки должны добавляться в конфигурационные файлы.

Запрещается жёстко кодировать:

* пути;
* размеры;
* параметры генерации;
* шаблоны prompt;
* workflow.

---

# Prompt Templates

Все шаблоны prompt должны храниться в YAML.

Изменение качества генерации должно происходить без изменения Python-кода.

---

# Workflow

Все workflow должны храниться отдельно от кода.

Добавление нового workflow не должно требовать изменения существующей логики.

---

# Документирование

Если изменение влияет на публичное поведение проекта, необходимо обновить соответствующие документы:

* `PROJECT_SPEC.md`;
* `ARCHITECTURE.md`;
* `ROADMAP.md`;
* `README.md`.

---

# Тестирование

Перед завершением работы необходимо:

* убедиться, что существующее поведение не нарушено;
* при необходимости добавить или обновить тесты;
* проверить обработку ошибок.

---

# Код

Каждый новый код должен:

* быть читаемым;
* быть расширяемым;
* соответствовать SOLID;
* соответствовать DRY;
* использовать `pathlib`;
* использовать `logging`;
* использовать `type hints`;
* иметь понятные имена.

---

# Недопустимо

Запрещается:

* оставлять необъяснённые TODO;
* использовать `pass` вместо реализации без причины;
* дублировать функциональность;
* смешивать инфраструктурный код и бизнес-логику;
* добавлять зависимости без необходимости;
* нарушать существующую архитектуру без согласования.

---

# Принципы взаимодействия AI-агентов

AI-агент должен:

* объяснять архитектурные решения перед реализацией;
* предлагать улучшения отдельно от обязательной реализации;
* не переписывать большие части проекта без необходимости;
* учитывать уже существующие документы проекта;
* стремиться к минимальным, безопасным изменениям.

Если задача слишком велика для одного ответа, агент должен разбить её на последовательные этапы, сохраняя работоспособность проекта после каждого из них.

---

# Качество важнее скорости

При выборе между:

* быстрым решением;
* качественной архитектурой;

всегда выбирать качественную архитектуру.

---

# Совместимость

Проект должен оставаться:

* модульным;
* расширяемым;
* документированным;
* пригодным для публикации как open-source.

Любое изменение должно стремиться сохранить обратную совместимость, если это не противоречит целям проекта.

---

# Цель проекта

Создать профессиональный инструмент, который позволит Xiaomi MiMo Code автоматически использовать локальную генерацию изображений и другие мультимодальные возможности при разработке современных веб-приложений, сохраняя высокое качество архитектуры, кода и документации.
