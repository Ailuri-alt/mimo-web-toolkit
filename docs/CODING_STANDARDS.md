# CODING_STANDARDS.md

# MiMo Web Toolkit

Версия: 1.0

---

# Назначение

Данный документ определяет единые правила разработки проекта **MiMo Web Toolkit**.

Все изменения в проекте должны соответствовать этим правилам.

Если возникает конфликт между скоростью разработки и качеством архитектуры, всегда выбирать качество архитектуры.

---

# Общие принципы

При разработке использовать:

* Python 3.11+
* PEP 8
* SOLID
* DRY
* KISS
* Composition over Inheritance
* Explicit is Better than Implicit

Код должен быть понятным через год без дополнительных пояснений.

---

# Архитектура

Использовать модульную структуру.

Каждый модуль должен отвечать только за одну задачу.

Не допускается объединять несколько независимых компонентов в одном файле.

Каждый пакет должен содержать понятную структуру.

---

# Размер файлов

Рекомендуемый размер:

* до 300 строк — отлично;
* до 500 строк — допустимо;
* более 500 строк — только при наличии веских причин.

При росте файла необходимо рассмотреть его разделение.

---

# Размер функций

Функции должны быть небольшими.

Рекомендуемый размер:

* 10–30 строк;
* до 50 строк — допустимо;
* более 50 строк — требуется объяснение.

Если функция становится слишком большой, разделить её на несколько.

---

# Имена

Использовать понятные имена.

Хорошо:

* image_generator
* workflow_loader
* prompt_engine

Плохо:

* helper
* utils2
* manager_new
* temp

---

# Pathlib

Запрещается использовать os.path.

Использовать только pathlib.

Пример:

```python
from pathlib import Path

PROJECT_ROOT = Path(__file__).resolve().parent.parent
```

---

# Type Hints

Все публичные функции должны иметь type hints.

Например:

```python
def generate_image(
    request: ImageRequest
) -> Path:
    ...
```

Использовать встроенные типы Python (`list[str]`, `dict[str, Any]`, `Path | None` и т. п.), если нет причин поддерживать старые версии языка.

---

# Dataclasses

Использовать `@dataclass` для структур данных.

Например:

* ImageRequest
* WorkflowInfo
* PromptTemplate

---

# Pydantic

Использовать только там, где действительно нужна валидация входных данных или конфигурации.

Не применять Pydantic без необходимости.

---

# Конфигурация

Все параметры должны храниться в YAML.

Запрещается:

* жёстко прописывать пути;
* жёстко прописывать размеры;
* жёстко прописывать prompt'ы;
* жёстко прописывать workflow.

---

# Логирование

Использовать стандартный модуль `logging`.

Не использовать `print()` для диагностики.

Каждый модуль должен получать именованный логгер.

Логировать:

* запуск;
* завершение;
* ошибки;
* предупреждения;
* время выполнения операций.

---

# Исключения

Не использовать пустые обработчики:

```python
except:
    pass
```

Каждое исключение должно:

* логироваться;
* содержать понятное сообщение;
* при необходимости оборачиваться в собственный тип исключения.

---

# Собственные исключения

Создать пакет:

exceptions/

Использовать специализированные исключения.

Например:

* WorkflowError
* PromptError
* ComfyConnectionError
* ImageGenerationError

---

# Импорт

Группировать импорты:

1. стандартная библиотека;
2. сторонние библиотеки;
3. внутренние модули проекта.

Между группами оставлять пустую строку.

---

# Документация

Каждый публичный класс должен иметь docstring.

Каждая публичная функция должна содержать описание:

* назначения;
* параметров;
* возвращаемого значения;
* возможных исключений (если это важно).

При необходимости приводить небольшой пример использования.

---

# Комментарии

Комментарии должны объяснять **почему** принято решение, а не повторять очевидное.

Избегать комментариев, которые быстро устаревают.

---

# Тестирование

Каждый новый модуль должен сопровождаться тестами там, где это практически оправдано.

Использовать `pytest`.

Тесты должны быть независимыми друг от друга.

---

# MCP

Каждый инструмент MCP должен:

* иметь отдельный модуль;
* иметь описание;
* иметь строгую схему входных параметров;
* возвращать структурированный результат;
* корректно обрабатывать ошибки.

---

# ComfyUI

Все обращения к ComfyUI должны проходить только через единый клиент (`comfy_client.py`).

Никакой другой модуль не должен выполнять HTTP-запросы к ComfyUI напрямую.

---

# Prompt Engine

Все шаблоны должны храниться только в YAML.

Python-код не должен содержать длинных текстовых prompt'ов.

---

# Workflow Engine

Workflow не должны быть встроены в код.

Все workflow должны храниться в отдельных JSON-файлах.

---

# Работа с файлами

Все создаваемые файлы должны использовать `pathlib.Path`.

Пути формировать относительно корня проекта или каталогов, заданных в конфигурации.

---

# Оптимизация изображений

После генерации изображений необходимо:

1. проверить успешность создания;
2. при необходимости оптимизировать;
3. сохранить в целевом формате;
4. вернуть путь к итоговому файлу.

---

# Принятие решений

Если существует несколько вариантов реализации, выбирать тот, который:

1. проще поддерживать;
2. легче тестировать;
3. лучше расширяется;
4. меньше связан с другими компонентами.

---

# Работа с этапами

Перед началом каждого этапа:

1. объяснить архитектурное решение;
2. показать дерево файлов.

После завершения этапа:

1. перечислить созданные файлы;
2. перечислить изменённые файлы;
3. кратко описать результат;
4. предложить следующий этап.

---

# Запрещается

Запрещается:

* использовать временные решения без объяснения;
* оставлять неиспользуемый код;
* дублировать функциональность;
* смешивать бизнес-логику и инфраструктурный код;
* использовать «магические числа» и строки без вынесения в конфигурацию;
* менять публичные интерфейсы без документированного обоснования.

---

# Цель

Поддерживать единый стиль разработки на протяжении всего жизненного цикла проекта, обеспечивая читаемость, расширяемость, тестируемость и предсказуемость архитектуры.
